|08.09.2026|Архитектор (Claude) рекомендовал JSON вместо ChromaDB для хранилища эталона (REQ-18), оценивая задачу изолированно от остальной архитектуры продукта|Решение по инфраструктурному компоненту нельзя оценивать в отрыве от того, что происходит в остальной системе — маржинальная стоимость переиспользования уже поднятой инфраструктуры (ChromaDB для RAG) часто ниже, чем стоимость новой, даже "простой"|Владелец продукта настоял на ChromaDB, что задним числом оказалось верным после появления RAG-пайплайна|Для будущих архитектурных решений — явно проверять «а что ещё в системе уже требует похожую инфраструктуру», а не оценивать задачу в вакууме. Формализовано в `role-claude.md`, раздел 1.6, пункт 7|
|08.09.2026|Референс \[8] в ТЗ v1.2 (REQ-05.1) утверждал наличие постоянного бесплатного тарифа Yandex SpeechKit "100 000 сообщений/мес" — при проверке по официальной документации не подтвердилось (только пробный период, далее платно)|Perplexity принял вторичный источник/агрегатор за достаточное подтверждение количественного факта о тарифе, без проверки по первоисточнику (официальная документация вендора)|Claude обнаружил расхождение при архитектурном решении по транскрипции (веб-поиском) и скорректировал выбор в пользу self-hosted GigaAM-v3/Whisper|Добавить в `role-perplexity.md` требование: количественные тарифные факты (лимиты free tier, цены) проверять только по официальной документации вендора, не по агрегаторам/статьям, независимо от количества источников, где факт повторяется|
|08.09.2026|Несколько архитектурных пробелов (тип хранилища для новых сущностей, необходимость бэкапов, модель развёртывания UI, анти-спам для публичных точек входа) обнаруживались только после прямого вопроса владельца продукта, а не проактивно со стороны Архитектора|В `role-claude.md` не было формализованного набора проверок, которые Оркестратор обязан проходить при каждом новом архитектурном решении — полагались на то, что архитектор "сам заметит"|Введён раздел 1.6 «Проактивный чек-лист архитектора» в `role-claude.md`, обязательный к применению в любом будущем проекте|Явный чек-лист из 7 пунктов теперь встроен в роль постоянно, а не восстанавливается по памяти от проекта к проекту|
|14.09.2026|TASK-002: Acceptance Criteria задачи не специфицировали поведение `create\_client\_project` при частичном сбое создания структуры (неатомарность) — выявлено ChatGPT только на этапе ревью, а не при формулировке AC|Оркестратор (Claude) формулировал AC-1/AC-2 без требования к атомарности операции; для операций над группой файлов/папок failure-сценарии не проговаривались, аналогично упущению REQ-06 (нужна ли точка ручной проверки)|Замечание классифицировано как не критическое, отложено с явным триггером «первое реальное обращение с симптомом ProjectAlreadyExistsError на пустой папке»; кандидат-решение — rollback через `shutil.rmtree` в failure-ветке try/except|В `role-claude.md`, раздел 1.6 «Проактивный чек-лист архитектора» — добавить пункт: для любой операции, создающей группу файлов/папок, AC должен явно фиксировать требование к атомарности (rollback при частичном сбое) либо её осознанный отказ|
|14.09.2026|Первый коммит проекта (TASK-002) был отправлен напрямую в ветку `main`, минуя feature-branch `task/TASK-002-project-structure` и PR — отступление от GitHub Flow, зафиксированного в общем DoD|В протоколе владельца процесса отсутствовал обязательный pre-flight шаг «создать feature-branch ПЕРЕД первым коммитом»; GitHub Desktop по умолчанию открывается на текущей ветке (main), и это состояние не было помечено как опасное|Принято как есть (переписывание истории после push не оправдано рисками); зафиксировано правило: начиная с TASK-003 первое действие в GitHub Desktop — New branch|В `handoff-cheatsheet.md` — добавить обязательный pre-flight чек-лист для владельца процесса перед каждым коммитом: (1) проверить текущую ветку, (2) создать feature-branch по конвенции `task/TASK-XXX-имя`, (3) убедиться, что во вкладке Changes только файлы текущей задачи, (4) коммит, (5) push, (6) PR, (7) merge только после зелёных тестов Kimi|
