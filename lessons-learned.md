# lessons-learned.md

**Последнее обновление:** 08.09.2026

> Основное назначение файла — фиксировать системные ошибки **агентов в реальных
> рабочих циклах** и переносить исправление в соответствующий `role-*.md`.

| Дата | Ошибка | Корень проблемы | Решение | Как предотвратить |
|---|---|---|---|---|
| 04.09.2026 | `role-perplexity.md` в первой версии не различал два разных стейкхолдера: владелец продукта vs внешний клиент | Не был заложен явный elicitation-этап для случая, когда сам агент помогает определить требования к новому продукту «с нуля» | Добавлен раздел 1.6 и 2.2a (режим Stakeholder Interview) в `role-perplexity.md` | Для любого нового `role-*.md`, где агент формирует артефакт «с нуля» — явно указывать: кто стейкхолдер и нужен ли elicitation-этап |
| 04.09.2026 | Входы/выходы системы в README.md были на грани того, чтобы попасть в ТЗ как подтверждённый факт, хотя являлись лишь предположением владельца продукта | Классическая BABOK-ошибка elicitation: наследование гипотез заказчика как требований без валидации | Входы/выходы в README.md явно помечены значком 🔶 «рабочая гипотеза» | При создании README.md для новых продуктовых задач — по умолчанию помечать входы/выходы как гипотезу до elicitation |
| 04.09.2026 | LLM-агенты в диалоге отвечают инкрементально и не производят единый структурированный блок для хендоффа без явной просьбы | В `role-*.md` не было явного шага «финальной сборки» | Введён единый паттерн «Триггер финальной сборки» во всех ролевых промптах | При создании любого нового `role-*.md` — обязательно включать подраздел с триггер-фразой финальной сборки |
| 08.09.2026 | ТЗ v1.2 не содержало явного requirement на человеческую проверку между вероятностным анализом (субагенты, TASK-009/011/012/013/016) и финализацией отчёта | При elicitation (`role-perplexity.md`) не был задан вопрос "нужна ли точка ручной верификации между AI-рассуждением и финальным артефактом" — упущение в Stakeholder Interview для продуктов с probabilistic-компонентами | Добавлен гейт TASK-025/026 постфактум, на этапе декомпозиции | Для будущих продуктов: в раздел 2.2a `role-perplexity.md` добавить обязательный вопрос категории "Обработка" — "нужна ли и на каком этапе точка человеческой проверки, если в пайплайне есть LLM-рассуждение" |
| 08.09.2026 | Архитектор (Claude) рекомендовал JSON вместо ChromaDB для хранилища эталона (REQ-18), оценивая задачу изолированно от остальной архитектуры продукта | Решение по инфраструктурному компоненту нельзя оценивать в отрыве от того, что происходит в остальной системе — маржинальная стоимость переиспользования уже поднятой инфраструктуры (ChromaDB для RAG) часто ниже, чем стоимость новой, даже "простой" | Владелец продукта настоял на ChromaDB, что задним числом оказалось верным после появления RAG-пайплайна | Для будущих архитектурных решений — явно проверять «а что ещё в системе уже требует похожую инфраструктуру», а не оценивать задачу в вакууме. Формализовано в `role-claude.md`, раздел 1.6, пункт 7 |
| 08.09.2026 | Референс [8] в ТЗ v1.2 (REQ-05.1) утверждал наличие постоянного бесплатного тарифа Yandex SpeechKit "100 000 сообщений/мес" — при проверке по официальной документации не подтвердилось (только пробный период, далее платно) | Perplexity принял вторичный источник/агрегатор за достаточное подтверждение количественного факта о тарифе, без проверки по первоисточнику (официальная документация вендора) | Claude обнаружил расхождение при архитектурном решении по транскрипции (веб-поиском) и скорректировал выбор в пользу self-hosted GigaAM-v3/Whisper | Добавить в `role-perplexity.md` требование: количественные тарифные факты (лимиты free tier, цены) проверять только по официальной документации вендора, не по агрегаторам/статьям, независимо от количества источников, где факт повторяется |
| 08.09.2026 | Несколько архитектурных пробелов (тип хранилища для новых сущностей, необходимость бэкапов, модель развёртывания UI, анти-спам для публичных точек входа) обнаруживались только после прямого вопроса владельца продукта, а не проактивно со стороны Архитектора | В `role-claude.md` не было формализованного набора проверок, которые Оркестратор обязан проходить при каждом новом архитектурном решении — полагались на то, что архитектор "сам заметит" | Введён раздел 1.6 «Проактивный чек-лист архитектора» в `role-claude.md`, обязательный к применению в любом будущем проекте | Явный чек-лист из 7 пунктов теперь встроен в роль постоянно, а не восстанавливается по памяти от проекта к проекту |
| 08.09.2026 | При реализации TASK-002 первый коммит ушёл напрямую в `main`, минуя feature-branch (нарушение GitHub Flow, принятого 04.09.2026) | Ручной перенос кода из JSON DeepSeek в файлы не имел зафиксированного пошагового протокола — шаг «создать ветку до первого коммита» не был явно описан нигде, кроме общего упоминания принципа GitHub Flow | Введён раздел 2.4 в `role-deepseek.md` — пошаговый протокол GitHub Desktop с явным Шагом 1 «создать ветку ПЕРЕД первым коммитом» и прямой ссылкой на этот инцидент | Для любого процесса, где человек вручную выполняет серию действий по памяти (не автоматизировано) — зафиксировать точный пошаговый протокол в соответствующей role-*.md, а не полагаться на общее упоминание принципа |
