## 3. Архитектурные решения

### 3.1 Транскрипция (REQ-05.1)
**Решение:** GigaAM-v3 (self-hosted, MIT) — основной; Whisper (self-hosted) — резерв.
**Обоснование:** GigaAM-v3 существенно точнее на русском (WER 9.2% vs 25.1% у Whisper-large-v3, официальный бенчмарк). Оба варианта — self-hosted, без лимитов и платных зависимостей.
**Важная находка:** референс ТЗ v1.2 о бесплатном тарифе Yandex SpeechKit (100 000 сообщений/мес) не подтверждён официальной документацией — реально бесплатен только пробный период, далее платно. Зафиксировано в `lessons-learned.md`.
**Отклонено:** Yandex SpeechKit, mymeet.ai (лимит 180 мин/мес), TurboScribe (лимит файлов/день).

### 3.2 Хранилище эталона (REQ-18)
**Решение:** ChromaDB (self-hosted, Apache 2.0) с локальной embedding-моделью (`sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`, без OpenAI API).
**История решения:** Архитектор изначально рекомендовал JSON (YAGNI). Владелец продукта переопределил на ChromaDB. После введения RAG (волна 3) решение подтвердилось как более дальновидное — маржинальная стоимость переиспользования уже поднятой инфраструктуры ChromaDB для RAG оказалась ниже стоимости отдельного JSON-решения.
**Отклонено:** JSON-библиотека (отменена), графовая БД.

### 3.3 LLM-провайдер для аналитического слоя (REQ-07–12)
**Решение:** Переключаемая комбинация провайдеров через единый интерфейс `AnalysisLLMProvider`:

| Провайдер | Лимит free tier | Проверено |
|---|---|---|
| Gemini API (прямой) | ~1500 запросов/день, 1M TPM (Gemini 2.5 Flash) | Официальная документация Google AI Studio |
| OpenRouter (`:free` модели) | 20 запросов/мин, **50 запросов/день — общий лимит на весь аккаунт**, не per-модель | Официальная документация OpenRouter |
| Groq (опционально) | ~30 запросов/мин, до 14 400 запросов/день (зависит от модели) | Официальная документация Groq |

**Обоснование:** Независимые лимиты РАЗНЫХ вендоров дают реальную возможность «переключаться, пока не кончатся токены» — переключение моделей ВНУТРИ одного OpenRouter-аккаунта общий лимит не увеличивает.
**Риск конфиденциальности:** free tier Gemini использует данные запросов для обучения — принято условие: реальные клиентские данные не передаются до перехода на платный tier/self-hosted LLM. MVP — только синтетические/обезличенные данные.
**Отклонено:** GigaChat API (разовый грант 1 млн токенов/год), OpenRouter как единственный источник.

### 3.4 RAG-пайплайн для клиентских документов
**Решение:** Голый Python поверх ChromaDB (chunking → embedding → retrieval), НЕ LangChain/LlamaIndex.
**Обоснование:** Образовательная цель (понять механику RAG) + снятие ограничения контекстного окна LLM. Прозрачность реализации важнее готовых абстракций фреймворков.
**Изоляция данных:** отдельная ChromaDB-коллекция на каждый client_id (TASK-028), физически отделена от коллекции эталона (TASK-022).
**Отклонено:** LangChain/LlamaIndex (скрывают механику), embedding через OpenAI API (платно).

### 3.5 Точка ручной проверки консультантом
**Решение:** Обязательный гейт (TASK-025/026) между блоком анализа и генерацией отчёта — теперь реализуется как экран №6 веб-приложения (изначально планировался как YAML-файл, см. раздел 3.10).
**Обоснование:** AI-субагенты выдают вероятностный результат — нужна контрольная точка перед финализацией отчёта. Пробел исходного ТЗ v1.2, зафиксирован в `lessons-learned.md`.
**Обучающий контур:** правки консультанта — второй источник обучающего сигнала для TASK-024 наравне с фидбеком клиента (REQ-20), равные веса на MVP.

### 3.6 Разделение хранилищ (Polyglot persistence)

| Критерий | ChromaDB | SQLite |
|---|---|---|
| Тип запроса | «Найди похожее по смыслу» | «Найди заявки со статусом X, отсортируй по дате» |
| Что хранит | `CHUNK` (RAG-индекс клиента), `BENCHMARK_PATTERN` (эталон) | `CLIENT`, `CLIENT_APPLICATION`, `USER`, `REPORT`, `REVIEW_EDIT`, `LLM_PROVIDER_CONFIG` |
| Гарантии целостности | Слабые, не классический ACID | ACID — критично для статусов заявок |
| Почему не одна БД на всё | Хранить статусы/роли в ChromaDB технически можно, но без нормальных фильтров/JOIN/транзакций; семантический поиск в SQLite требует нестандартных расширений | — |

**Решение:** обе базы одновременно, каждая под свою задачу (polyglot persistence — стандартная практика, не компромисс). MySQL отклонён — требует отдельного сервера, избыточно для одного MVP-приложения; SQLite самодостаточен файлом на диске.

### 3.7 Резервное копирование (НФТ)

**Правило 3-2-1 (адаптировано под решение владельца — без offsite-копии на MVP):**

| Копия | Реализация в проекте |
|---|---|
| 1 — рабочая | Локальный диск, как обычно |
| 2 — другой носитель, автоматически | Ежедневный архив (TASK-031): ChromaDB snapshot + SQLite + `history/`, ротация 7 дней |
| 3 — вне машины | **Отложено** по решению владельца — не требуется для MVP |

**Практики, заложенные в TASK-031:**
- Автоматизация через cron (не вручную)
- Ротация: 7 ежедневных копий, старые удаляются
- Бэкап ChromaDB через её собственный snapshot API, не сырое копирование файлов во время записи (риск повреждения)
- Недоступность второго носителя не должна тихо проваливать весь бэкап — primary всё равно выполняется, ошибка логируется явно

**НФТ для ТЗ (ISO 25010 — Reliability/Recoverability):**
> Система должна автоматически создавать резервную копию накопленного эталона и данных заявок клиентов не реже раза в сутки, с копией на втором носителе, ротация ≥7 дней.

### 3.8 Заявка и статусная модель
**Решение:** Новая сущность `CLIENT_APPLICATION` с полем `status` (11 состояний, раздел 7), SQLite-хранение, матрица допустимых переходов в конфиге (TASK-030).
**Обоснование:** Прозрачность процесса диагностики для клиента и консультанта.

### 3.9 Telegram-бот — анти-спам
**Решение:** Приём свободного текста только в состоянии ожидания вопроса 3 (боль/цель); ограничение длины ответа (500 символов, конфигурируемо). Явно НЕ добавлены: rate limit на пользователя, глобальный rate limit сообщений/сек, CAPTCHA — узкий сценарий (кнопки + один свободный текст) их не требует.

### 3.10 Единое веб-приложение (Вариант Б)
**Решение:** Flask + Jinja2 + htmx, серверный рендеринг (без SPA-фреймворка, без build-процесса), WSGI-сервер waitress.
**Аутентификация:**

| Роль | Механизм | Почему |
|---|---|---|
| Консультант, Администратор | Логин/пароль (Flask-Login + Werkzeug password hashing) | Постоянные пользователи, заходят регулярно |
| Клиент, Сотрудник клиента | Magic link (временная подписанная ссылка, `itsdangerous`) | Заходят редко, разово — регистрация избыточна |

**Обоснование:** единый веб-слой строится один раз вместо патчворка файлов/бота/CLI по каждой отдельной точке взаимодействия.
**Следствие:** задача TASK-033 (изолированный Flask-сервис только для переключения LLM-провайдера) **упразднена** — становится экраном №9 внутри единого приложения.
**Отклонено:** SPA на React (лишний build-процесс для self-hosted MVP), единый логин для всех ролей.

## 8. Веб-приложение — полная спецификация экранов (13 экранов)

Flask + Jinja2 + htmx. Аутентификация: логин (Консультант/Администратор), magic-link (Клиент/Сотрудник).

### Экран 0 — Вход
**Роль:** Консультант, Администратор. **Доступ:** логин/пароль.
Элементы: поля логин+пароль, чекбокс «запомнить меня», ссылка «забыли пароль» (сброс через email — опционально за MVP-скоупом).
Действие: «Войти» → Дашборд (экран 1). Данные: `USER`.

### Экран 1 — Дашборд / Список заявок
**Роль:** Консультант.
Элементы: таблица (Клиент | Статус — цветной бейдж | Дата создания | Дата изменения), фильтр по статусу (11 значений), поиск по клиенту, кнопка «+ Новая заявка», счётчики («В работе: N», «Ожидают проверки: N», «Требуют внимания (ERROR): N»).
Действия: клик по строке → экран 2; «+ Новая заявка» → форма создания. Данные: `CLIENT_APPLICATION`, `CLIENT`.

### Экран 2 — Карточка заявки
**Роль:** Консультант (полная версия), Клиент (упрощённая, через magic-link).
Консультант: шапка (клиент, статус, дата), прогресс-бар из 5-6 ключевых стадий, история статусов (таблица дата/переход/кто), вкладки (Материалы→экран 3, Сотрудники, Анализ→экран 6, Отчёт→экран 7), кнопка «Отменить заявку».
Клиент: только прогресс-бар + статус человеческим языком, без внутренних деталей.
Данные: `CLIENT_APPLICATION`, `status_history`, связанные `MATERIAL`/`EMPLOYEE`/`REPORT`.

### Экран 3 — Загрузка материалов
**Роль:** Консультант.
Элементы: drag-and-drop зона / кнопка выбора файлов, список загруженных (имя, тип, дата, статус обработки для аудио), индикатор допустимых форматов (DOC/DOCX/TXT/MD/XLS/XLSX/аудио).
Действие: «Загрузить» → TASK-003, обновляет manifest; фоновый вызов TASK-007 после каждой загрузки. Данные: `MATERIAL`.

### Экран 4 — Проверка полноты / Гейт «Продолжить?»
**Роль:** Консультант.
Элементы: список требуемых типов с чекмарками (✅/❌), пояснение по каждому пробелу, кнопка «Продолжить, даже если не всё готово» (с предупреждением), кнопка «Приостановить заявку».
Действие: «Продолжить» → статус → `ANKETA_CREATION`. Данные: результат TASK-007.

### Экран 5 — Анкета сотрудника
**Роль:** Сотрудник клиента. **Доступ:** magic-link, ссылка отправляется консультантом вручную (вне системы на MVP).
Элементы: приветствие (компания, департамент), список вопросов анкеты (текстовые поля), опционально кнопка «Прикрепить аудио», прогресс «Вопрос 3 из 8».
Действие: «Отправить ответы» → сохранение, вызов TASK-006 при наличии аудио, уведомление консультанту. Данные: `EMPLOYEE`, `DIGEST`. Особое: ссылка одноразовая/с истекающим сроком.

### Экран 6 — Проверка анализа консультантом
**Роль:** Консультант. *(Замена YAML-файла на веб-форму, см. решение 3.5)*
Элементы: карточки найденных процессов (название, департамент, скор, классификация — каждое поле редактируемое инлайн), маркер `[ФАКТ]/[ВЫВОД]/[ГИПОТЕЗА]/[ПРЕДПОЛОЖЕНИЕ]` рядом с полем + раскрывающаяся реальная цитата-источник, секции (Зрелость, AS-IS/TO-BE, Дорожная карта, ROI), кнопка «Одобрить и сформировать отчёт» (TASK-018-021), кнопка «Отправить на повторный анализ» (статус → `ANALYSIS`).
Данные: `PROCESS`, `CLAIM`, `MATURITY_SCORE`, `AS_IS_TO_BE`, `ROADMAP_PHASE`, `ROI_ESTIMATE`. Особое: каждая правка = запись в `REVIEW_EDIT` → TASK-024.

### Экран 7 — Просмотр отчёта
**Роль:** Клиент (magic-link), Консультант.
Элементы: встроенный просмотрщик HTML-версии отчёта (TASK-019), кнопки скачивания PDF/DOCX/MD. Данные: `REPORT`.

### Экран 8 — Валидация гипотез
**Роль:** Клиент.
Элементы: список гипотез (`Claim` типа `HYPOTHESIS`), переключатель «Подтверждаю/Отклоняю» + комментарий, кнопка «Отправить фидбек».
Действие: «Отправить» → TASK-024 с `source=CLIENT_VALIDATION`, статус → `CLOSED_COMPLETED`. Данные: `CLAIM`, обновление `BENCHMARK_PATTERN`.

### Экран 9 — Переключатель LLM-провайдера
**Роль:** Администратор. *(Ранее — отдельная задача TASK-033, теперь часть единого приложения)*
Элементы: выпадающий список Провайдер (Gemini/OpenRouter/Groq) → зависимый список моделей, текущий активный — выделен, индикатор последних ошибок (например, «OpenRouter: лимит исчерпан сегодня в 14:32»), кнопка «Применить».
Данные: `LLM_PROVIDER_CONFIG`. Действие: запись в SQLite (TASK-032), эффект — на следующий вызов анализа, без перезапуска.

### Экран 10 — Настройка весов скоринга и порогов
**Роль:** Администратор.
Элементы: слайдеры/поля для 5 критериев скоринга (repeatability, data availability, explainability, time volume, error cost) с визуальной суммой «=100%», порог explainability для правила «не может быть AGENT», порог confidence для retrieval (TASK-029).
Особое: изменения влияют на новые заявки, не пересчитывают уже начатые (явное предупреждение на экране).

### Экран 11 — Управление пользователями и ролями
**Роль:** Администратор.
Элементы: таблица (имя, email, роль, дата последнего входа), кнопка «+ Пригласить пользователя» (форма email+роль → временный пароль/ссылка), кнопка деактивации.
Данные: `USER`.

### Экран 12 — Статус системы и бэкапов (опционально для MVP)
**Роль:** Администратор.
Элементы: дата и статус последнего бэкапа (TASK-031), кнопка «Запустить бэкап сейчас», размер накопленного эталона (метрика роста TASK-022).
Особое: явный кандидат на «Should have», можно отложить первым при сокращении скоупа.
